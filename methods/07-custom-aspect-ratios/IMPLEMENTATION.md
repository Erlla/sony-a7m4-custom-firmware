### 2.1 选项表、注册表和列表模型

原四行 option 表在 `0x3FDA5F0`，每行 `0x80` 字节。保留四行，追加四个以 3:2 行为模板的新行，八行表放到 `0x9020000`。新行需要填写：

```text
+0x00 / +0x04  alias / identity
+0x08          文字 ID
+0x20 / +0x24  普通 / 选中图片 ID
+0x28 / +0x2C  0xFFFFFFFF
+0x34          私有选择 ID 4..7
```

修改 leaf descriptor `0x5936990`：`+0x54` 数量为 8；`+0x58` 的 `R_AARCH64_RELATIVE` addend 指向新表；`+0x78/+0x80/+0x88` 三个相对重定位绑定自定义 getter、setter、commit。对应 addend 在本文件的 `0xED9EE8/0xED9F18/0xED9F30/0xED9F48`，这些四个位置是**文件偏移**。

同时增加 option 注册记录 `0x9020400`（四条 `<IIQ>`，指针字段追加相对重定位）、alias 表 `0x9020440`、父叶映射 `0x9020468`。alias 表先保留区间分隔项 `(5631,5592)`，再放四个 `(5632+i,5632+i)`；父叶映射为 `(5632+i,33)`。同步更新 `.rela.dyn`、`DT_RELASZ`，并链式调用已集成的注册器。

### 2.2 字符串与图标资源

四个运行时文字 ID `0x0200AB60..63` 在字符串容器中存为 `0x1E00AB60..63`，内容依次为 `17:6`、`65:24`、`5:4`、`7:6`。对 68 个匹配银行同时补齐：

```text
magic       = "uxc\x07"
count       = u32(+12) / 0x1001，须验证无余数
id_base     = 0x1E000000 + (u16(+10) << 13)
index_table = +16，每项 u16；0xFFFF 表示空槽
data_base   = align4(16 + 2*count)
record      = data_base + 4*index_word
record 内容 = u32 stored_id + UTF-8 字符串 + NUL，按四字节对齐
```

先验证目标 ID 属于该银行并且索引为空，再追加记录和更新索引，保留已有记录。此处列出本功能需要的四个标签；最终文件身份以清单为准。

两个图片容器各增加八个图标，索引 `0x1E90..0x1E97`，stored key 为 `0x1A000000+index`。图像容器 magic 为 `uxd\x07`；`count=u32(+12)&0x1FFF`，高位记录 `(count+1)//2`；索引和 `data_base` 的定位方式同上。

新增图标使用 20 B descriptor `<IIHHII>`：key、flags `0xC0000000`、宽 70、高 60、压缩流长度、相对于 `descriptor+4` 的 payload 偏移。移动 payload 区域时，维护普通 descriptor `+16` 及九宫格 descriptor `+36` 的相对偏移，保留其他图像数据。

位图为 little-endian RGBA4444：`(R4<<12)|(G4<<8)|(B4<<4)|A4`，可见宽 70，行 stride 80，60 行，共 `80*60*2=9600 B`。四种比例分别生成普通、选中图像，AP option 的 `+0x20/+0x24` 指向对应 ID。

压缩流按原资源解码器的 **4 KiB 输出块**编码：9600 B 拆成 **4096、4096、1408** 三块，每块独立字典，以 `F0` 开始、以 `00 00` 引用结束，引用不能跨块。每八个 token 使用一个低位优先 flag byte；literal 为 0，双字节引用为 1；引用 distance 12 bits，长度码 0..13 对应 3..16，14/15 对应 32/64。本参考 bank 还要求每块压缩输入不超过 4096 B。写入 descriptor 的实际压缩长度，并对三个块逐块解码验证总计 9600 B。

## 3. 保存选择并传递到拍摄任务

原厂参数、尺寸表与默认存储继续只看到原生 `0..3`；选用自定义比例时，它们看到 3:2 对应的 `0` / alias `126`。自定义选择由独立状态保存，不能把 4..7 直接写进所有原厂枚举消费者。

| 用途 | descriptor / 既有调用落点 | 最终有效入口 |
| --- | --- | --- |
| effective | `0x90104B8` | `0x9012178` |
| getter | `0x90105B4` | `0x90121B4` |
| setter | `0x90105E4` | `0x90121F4` |
| before apply | `0x9010618` | `0x901227C` |
| commit | `0x9010674` | `0x9012368` |

左列入口在最终文件通过 B 转入右列。原生 get/set/commit 分别为 `0x1C83A2C`、`0x1CA0E64`、`0x1CD2ED8`。

统一状态从 `0x9021000` 开始，四个 u32 为 `restore_claim, selection, persist_status, reserved`。`selection` 的 bit 3 表示完整发布，低三位存私有 ID，非自定义归零，高 28 bits 为递增 epoch；用 release/acquire 读写。显式选择优先于稍后完成的磁盘恢复，取消返回同一比例也更新 epoch，以失效旧预览结果。

getter 只有在原生值为 0 且私有 token 有效时返回 4..7；setter 接受 0..7，先发布状态，再向原生 setter 写 0 或原厂值。通用 apply 将自定义 alias 转成 126 交给原 broker。commit 执行原生提交并保存私有记录；浏览选择与最终保存不是同一动作，取消继续使用原菜单的还原流程。

设置记录位于 `/setting/custom_aspect_v2.dat`，内容为 16 B little-endian：

```text
u32 magic  = 0x32505243
u32 schema = 2
u32 id     = 4..7；0 表示取消自定义选择
u32 check  = ~id
```

恢复只接受恰好 16 B、无尾随数据、magic/schema/反码正确、id 为 4..7 且成功关闭的记录；id 0 用于清除选择，恢复时不启用私有比例。先写 `.tmp`、检查完整写入、fsync/close，再 rename 为正式文件，最后同步 `/setting`。绘制回调只读完成 token；恢复放在菜单/序列化入口或有效拍摄视图创建边界。

AP→CP 序列化保持一次调用的一致性：

1. 在指令点 `0x35F9764` 转入 `0x9010820`，保留原 `LDR W1,[X19,#8]` 的读取合同；原生值完成原转换/检查，有效私有 ID 冻结在本次栈帧 `X29+0x60`。
2. 在发送调用点 `0x35FA210` 转入 `0x901088C`，仅对冻结的 ID 4..7，将本次 packet `X1+8` 的单字节改为 wire 5..8。
3. 适配器在 `0x90108B4` 尾调用原发送函数 `0x35ED6E0`。最后发送时不重新读取全局选择，其余活跃寄存器、NZCV、LR 和消息字段保留原合同。

## 4. JPEG、HEIF 与 RAW 的处理边界

### 4.1 CP 接收与逐照片锁存

CP 接收 wire 5..8 后保存 `wire-1` 为私有 ID，并将原生处理值归一为 **2，即 CP 侧的原生 3:2**。AP 侧 3:2 的值为 0，两者不是同一枚举。其他 wire 继续走原转换并清除当前私有选择。

最终 12 处 CP 调用点先进入 resident dispatcher：代码地址 `0xBA5E38`，Thumb 指针 `0xBA5E39`。它按原 LR 分派并保存活跃寄存器/APSR，仅在模块 CRC 与可执行映射已核验、ready `0x1565EF0==1` 时调用扩展模块；未就绪则重放对应原指令或原 callee。模块 RX 为 `0x118000..0x11C000`。

| CP 调用点 VA | 新处理函数 Thumb 指针 | 用途 |
| --- | --- | --- |
| `0x3061CA` | `0x11B3E1` | 接收私有 wire，归一后写回 GFW `R5+0xA8` |
| `0xA049B0` | `0x11B4BD` | GFW 快照时冻结请求编号和比例 |
| `0xA03142` | `0x11B529` | 原 capture copy 后绑定照片任务 |
| `0x40511A`、`0x404632` | `0x11B7D1` | JPEG 主图、SCN 请求副本的几何 |
| `0x400E26` | `0x11B7D7` | JPEG THM 的输入 ROI 与目标适配 |
| `0xA0D012`、`0xA0D05C` | `0x11B805`、`0x11B831` | 主、副文件格式的输出宽高 |
| `0xA0D0E8` | `0x11B7FD` | HEIF packet 副本的三组 YC 几何 |
| `0xA0D25A` | `0x11B85D` | Notify 完成后清除任务比例 |
| `0xA06184` | `0x11B4A1` | 原 pool 释放成功后清除比例 |
| `0x3F4A48` | `0x11B7DD` | pool 初始化时清除 sidecar |

`aspect_selected_custom` 位于 `0x11EC38`，冻结请求和 ID 位于 `0x11EC3C/0x11EC40`。GFW copy 只在 source=`0x10FE5D0`、destination=`0x11C1F90`、长度 `0xD14`、source aspect 为 2 时锁存；原 memcpy `0x585FB8` 照常执行，编号来自 manager `0x11C1F68`。

capture copy 先调用原 `0x3ED2B9`，再检查 `task=destination-0x20`、source=`0x11C1F90`、`task+0x24==2`、`task+0x5550` 等于冻结请求编号，才设置任务的私有比例。

任务比例存放在外部 `task_ids=0x11EC44`，最多 490 个字节。按原 pool `0xFC1720` 的基址字段 `+0x10`、数量字段 `+4` 和对象步长 `0x60A8` 找索引，只接受对象起始指针。编码从该照片的 sidecar 读比例，不重新读取菜单值，也不往原 task 结构中插入字段。

### 4.2 居中 ROI 与编码对齐

几何结构为 12 B，小端的六个 u16：

```text
canvas_w +0x0, canvas_h +0x2
width    +0x4, height   +0x6
x        +0x8, y        +0xA
```

核心 `aspect_crop_geometry` 的 Thumb 指针为 `0x11B231`。保留 canvas、物理引用及像素所有权，只计算 valid ROI。主图接受精确 3:2；辅助图使用私有 AUX 标志 `0x100`，允许 `abs(2*width-3*height)<=16` 的原生近似尺寸。

设输入 valid 尺寸为 `sw,sh`，目标为 `p:q`，最终算法为：

```text
若 sw*q >= sh*p：
    h = align_down(sh, 8)
    w = ((h*p + q*8) // (q*16)) * 16
    若 w > sw，w = align_down(sw,16)
否则：
    w = align_down(sw,16)
    h = ((w*q + p*4) // (p*8)) * 8
    若 h > sh，h = align_down(sh,8)
```

中心 x 向下对齐 8 像素，再夹在原 valid ROI 和编码器读取范围均不越 canvas 的区间；y 同样按读取高度约束。canvas 宽度须为 128 的倍数，读取范围使用 `align_up(w,128)` 和 `align_up(h,8)`。目标最少 16×8，失败不改变输出。比例标签是标称比例，实际像素有上述整数舍入。

例如有效输入 7008×4672 时：

| 比例 | JPEG valid 输出尺寸 |
| --- | --- |
| 17:6 | 7008×2472 |
| 65:24 | 7008×2584 |
| 5:4 | 5840×4672 |
| 7:6 | 5456×4672 |

这四组尺寸已有 JPEG SOF 与解码检查；不是对所有尺寸档位都写死这四组数值。

### 4.3 JPEG 与 HEIF 分别在哪一层裁切

主、副格式字段在 `task+0x53E8/+0x53F0`，值为 **1=JPEG、2=RAW、4=HEIF**。

JPEG 仅在存在格式 1 且任务已锁存自定义比例时处理。主图源几何为 `task+0x5988`，SCN 为 `task+0x59EC`；在原 12 B memcpy 完成后改**目标编码请求副本**，不改原任务几何。THM 接在原缩放阶段，裁切输入后等比适配 160×120 目标画布，fit 宽向下对齐 4、高向下对齐 2，并居中填充。

Notify 的主、副格式字段为 packet `+0x1B0/+0x1BC`，对应 WH 为 `+0x1B6/+0x1C2`。wrapper 先调用原 `GetImageSize`（Thumb 指针 `0x41D62D`），只对格式 1/4 写裁切后 WH，格式 2 保留原值。

HEIF 在 `0xA0D0E8` 调用原 `0x5861F8`，复制 `task+0x55A4` 起的 `0x25C` 字节。仅在参数、格式 4 和任务 ID 均匹配时，修改目标副本 `+0xCC/+0xEC/+0x10C` 的主图、SCN、THM 几何。该副本位于 Notify packet `+0x1E8`，三个 packet 位置因此为 `+0x2B4/+0x2D4/+0x2F4`。

原生 AVCAM receiver 将其接到 CamMP context `+0x3BC/+0x3C8/+0x3D4`，DMM import 后进入主图和辅助图输入。原 `0x1FEA58` 生成各 slot 几何，`0x1FEE00` 将每个 PIN 扩成十个 halfword 的 SDF 参数：canvas WH、源 xy、valid WH、内嵌 xy/WH。这里的两个地址是下节约定的 AVCAM 镜像偏移。后续继续走原生 DMM/SDF/MC/HEIF 编码链。

### 4.4 AVCAM 的五个修改窗口

AVCAM 使用 **AArch64**。下表与本节 `0x1Exxxx/0x1Fxxxx` 地址均为指定 `av-cam.bin` 的**镜像/文件偏移**，该代码映射的链接基址是 `0xFFFFFFC001000000`；其他段需查 LIRO 映射。镜像长度与 LIRO 头保持原样。

| 文件偏移 | 字节数 | 修改内容 |
| --- | --- | --- |
| `0x1EC728` | 4 | 主 JPEG 格式构造 BL 指向 `0x1ED418` wrapper |
| `0x1EC74C` | 4 | 副 JPEG 格式构造使用同一 wrapper |
| `0x1ED3F8` | 296 | 等价重排原尺寸 setter，保留单 slot 入口 `0x1ED438`，加入 wrapper |
| `0x1FED94` | 12 | HEIF SCN 目标 WH 取真实 source valid WH |
| `0x1FEF2C` | 104 | HEIF THM mode 2 按真实 ROI 适配 160×120 |

JPEG wrapper 先调用原格式构造 `0x1EC79C`，只在原生 aspect 为 2、目标 slot 格式为 JPEG、packet WH 与模板不同时更新对应尺寸。主/副 slot 在对象 `+0xA4/+0x224`，使用各自 packet WH；RAW slot 和 buffer 引用保留。

HEIF SCN 直接以实际输入 valid WH 为目标；THM 保留 160×120 canvas、原 fill `0x08000000` 和 flags `0x0800`，按输入比例居中适配。这里修改的是编码输入和格式尺寸结构；没有额外修改 `libmpr.so` 的通用 EXIF/MakerNote 路径。

### 4.5 RAW 与验证范围

自定义选择向原生 RAW 路径提供 3:2，JPEG 改的是编码请求副本，Notify 的 RAW WH 和 AVCAM RAW slot 保持原值。因此保留的是 **RAW 主图的原始幅面**，不是承诺 ARW 的所有字节和嵌入预览完全不变。已有四组样片的 Bayer 存储为 7040×4688，默认有效区均为 7008×4672。

JPEG 尺寸核验应读取 SOF 和实际解码结果，不能只依赖 EXIF 或机内照片库的尺寸字段；本实现没有将这些元数据的全面同步列为完成范围。HEIF 三组 ROI 和原生几何路径已有离线回放，完整 HEIF 编码组合、RAW+HEIF 的辅助图生命周期及所有输出场景仍需分别实测。

## 5. 拍摄页遮罩：接入原生 guide 生命周期

拍摄页使用两套 presenter，分别有 585 和 442 个控件描述符。复用其中类型为 `0x3D` 的 guide 行：第一套 row 4，第二套 row 3。创建时检查原分配表和整个固定 arena 的容量，让该行生成真实控件，再登记其 parameter；原生其他行、图层和激活策略继续有效。

所有地址均为 AP VA，以下入口及跳转已在最终 `appFw.so` 中逐条核对：

| 用途 | 原入口 / 调用点 | 最终自定义目标 |
| --- | --- | --- |
| 第一套页面创建后登记 | `0x1DDAB68` | `0x9012BD8` |
| 第二套页面创建后登记 | `0x1E56B2C` | `0x9012CE4` |
| 第一套方向变化时重建 | `0x1D54898` | `0x90131D4` |
| 第二套方向变化时重建 | `0x1D547B0` | `0x90132E0` |
| 两套参数生产调用 | `0x1DDACC4`、`0x1E56C68` | `0x9012A98` |
| 两套设备能力判断 | `0x21853A0`、`0x2195FF0` | `0x9012F60`、`0x901301C` |
| 本次自定义静态照片的 guide 显示判断 | `0x244D2E0` | `0x9012BA0` |
| guide 更新入口 | `0x186D238` | `0x9012E68` |
| guide 析构入口 | `0x186D2AC` | `0x9012DF0` |

原生 producer 入口为 `0x244CF94`，完整 body/prologue 在 `0x244D1B4`。包装器只对已登记的 guide、静态照片模式和已发布自定义比例选择完整 body；其他路径调用原入口。`0x244D2E0` 的显示判断也只认本次包装器返回地址及 cookie，不能全局打开所有 guide。

登记状态从 `0x9021010` 开始，含 12 个槽，即两套页面各六层。每槽记录 parameter、generation 和已完成生产的 token。生产开始清除旧结果；完成时检查 generation 和当前选择；绘制时再次确认控件仍属于该槽。析构先撤销登记，旋转后按新控件重新登记。第一套旋转使用 presenter 的 layer `+0x278`，第二套使用 `+0x1E8`。

绘制读取当前控件中的完成参数，使用私有矩形副本调用原生方向处理 `0x186CA74` 和比例适配 `0x186CFE8`。比例表在 `0x9012F40`，按 17/6、65/24、5/4、7/6 排列。竖屏适配使用相应倒数；不改写原取景矩形。渲染读侧只读标量状态，不从该回调打开设置文件、等待恢复或重新取得原生模型锁。

## 6. Fn 与纵横比选择页：分别接入创建、旋转和刷新

这三个页面各有独立控件树。拍摄页 guide 的修改不能代替它们的绘制接入。

| 页面 | 控件数 / 空白图像行 | 初次创建调用点 | 方向重建调用点 | 原生 view 更新后的调用点 | 最终几何入口 |
| --- | --- | --- | --- | --- | --- |
| `scr7036_0009` 纵横比选择页 | 98 / row 4 | `0x1DF5198` | `0x1D49FB0` | `0x1DF55F8` | `0x9018000` |
| `scr0135_0001` Fn | 38 / row 6 | `0x1DE4E70` | `0x1D4ADB0` | `0x1DE5344` | `0x9017000` |
| `scr0135_0002` Fn | 76 / row 6 | `0x1E33F84` | `0x1D4ACD0` | `0x1E34734` | `0x9017490` |

三个几何旧入口分别在 `0x9013490`、`0x90150BC`、`0x90140B0`，最终文件在这些位置保留跳转至表中目标。移植时沿实际分支确认生效函数，不按保留符号表或段中任意旧函数推断。

创建包装器先验证当前页面的类型标记、控件数和分配容量，再仅启用指定行的真实图像控件；执行原 `BLR X8` 后恢复输入 flags。分配量按原生类型表以 128 B 单位累计，严格满足总量小于 arena 容量。参数对象存在不等于图像控件已经创建。

绘制包装器先完成原 `BLR X2` 更新，再绘制两块不透明黑色矩形。该空白图像已有九个 Sprite 矩形槽，只使用前两个，其余七个尺寸清零。保留原生下一次刷新隐藏/清除遮罩的行为，避免在取消、原厂比例或其他页面留下遮罩。

### 6.1 核对真实控件和快照

| 字段 | 选择页 | Fn 38 控件 | Fn 76 控件 |
| --- | --- | --- | --- |
| presenter 的 view 指针 | `+0x80` | `+0x40` | `+0x68` |
| presenter 的参数表指针 | `+0x88` | `+0x48` | `+0x70` |
| 当前方向 | `+0x8` | `+0x8` | `+0x8` |
| 快照方向 | `+0x72C0` | `+0x1388` | `+0x13C0` |
| 快照输出 route | `+0x1130` | `+0x3258` | `+0x5380` |

view 的 `+0x3E90` 是控件数，`+0x3EC8 + row*8` 指向该行 widget，`+0x3EA0` 为 arena 容量。参数指针应等于 `widget+0x1D8`，Sprite 为 `widget+0x248`。确认 Sprite 的 records `+0xD0` 非空、计数 `+0xD8 == 0x00090009`、没有 loaded resource 或 pending image。原生 `active=1` 且 image ID 为 `0xFFFFFFFF` 仍可以是空白图像；判断空闲必须结合这些字段。

选择页仅处理 leaf `presenter+0x5878 == 33`。比例从当前高亮 `presenter+0x71C8` 的 alias `5632..5635` 取得，直接对应四个新增比例，**不要求与已确认比例相同**。其已完成模型快照基址为 `presenter+0xF48`：

```text
x/y/w/h  : snapshot + 0x128 / 0x148 / 0x168 / 0x188
route    : snapshot + 0x1E8
format   : snapshot + 0x208
mapping  : snapshot + 0x5A60
direction: snapshot + 0x6378
```

Fn 使用当前已发布比例 token。在原模型锁 `0x2EE71E8` / 解锁 `0x2EE6EC4` 范围内，复制下列标量，**解锁后**再计算和绘图：

| 原生 getter | VA |
| --- | --- |
| YUV x、y、w、h | `0x290E1B0`、`0x290E1D8`、`0x290E200`、`0x290E228` |
| 输出 route / panel aspect | `0x290F850` / `0x291D34C` |
| 拍摄 mode / 原生 still aspect | `0x28ECDF8` / `0x28F3EB8` |
| direction / display mapping | `0x292DB14` / `0x28EFAF4` |

读取前后 token 必须一致，并检查 still mode `2`、原生 aspect `0`、当前页面与快照的方向及 route 相同。绘制不持有模型锁，也不保存模型指针到下一帧。

### 6.2 先在物理平面计算遮罩，再转换完整矩形

原始 YUV 取景区域始终位于 **640×480 物理平面**。竖屏 UI 的 480×640 是控件布局，不能拿它约束原始 YUV 的宽高。先核对 `x>=0,y>=0,w>0,h>0,x+w<=640,y+h<=480`。

显示像素并非所有 route 都是方形。按原生布局采用以下像素宽高比：

| route / format | 像素宽高比 `sn:sd` |
| --- | --- |
| route 0 | 1:1 |
| route 1、format 1 | 1:1 |
| route 1、format 2 | 4:3 |
| route 1、format 3 | 9:8 |

目标比例为 `N:D` 时，令 `n=N*sd`、`d=D*sn`。以下整数式与最终几何代码一致，对正值按最近整数计算单侧遮罩厚度：

```text
a = w*d; b = h*n
若 a > b：
    t = (a-b+d) // (2*d)
    bars = [(x,y,t,h), (x+w-t,y,t,h)]
否则：
    t = (b-a+n) // (2*n)
    bars = [(x,y,w,t), (x,y+h-t,w,t)]
```

若厚度为零或两侧厚度占满取景区，保留原生显示。之后使用**同一快照**中的 `direction` 和 `mapping` 转换每个 `(x,y,w,h)`：

```text
direction == 0：保持不变
(direction == 1) XOR (mapping == 4)：(480-y-h, x, h, w)
其余有效竖屏方向：                  (y, 640-x-w, h, w)
```

这与原 guide `0x186CB28` 的完整矩形变换相同，包含原点、远端边和宽高。方向 1↔2 可能只更新方向值而不重建控件，因此每次完整刷新仍需重算。Sprite 的局部旋转角为零也不表示页面未经过全局旋转。

绘制使用原生 widget position `0x1717260`、rect position `0x1716380`、rect size `0x17176D0`、rect color `0x1715A70`、widget mode `0x1716630`。额外回调保留被替换调用之后的整数寄存器、SIMD、NZCV、FPCR/FPSR 和栈对齐。

**自定义纵横比的实时取景通过遮罩标示裁切范围。进入部分参数设置页面时，预览可能暂时恢复为原始 3:2 画面；返回拍摄界面后，会恢复所选比例的遮罩。这只影响设置页面中的预览显示，JPEG/HEIF 成片仍按所选比例裁切，RAW 保持原始幅面。**

## 7. 集成与验证顺序

1. 提取目标 AP、CP、AVCAM 和 UI 资源，记录完整 SHA-256、ELF/LIRO 映射及每处原指令。其他合并功能占用的地址需一并纳入布局，不能只按显示版本选择补丁。
2. 先完成菜单表、ID 映射、私有状态与 AP→CP 消息合同，再接入逐任务裁切。保留原厂四个比例、确认/取消和 RAW 通道。
3. 对四个比例分别实现编码器对齐和缓冲区范围检查；在 JPEG 主图、辅助图及 HEIF 各个 YC 路径应用对应几何。
4. 同步更新 68 个字符串银行、两个图片容器及 AP 图标字段。对实际压缩块逐块解码，检查输出字节数和图像内容。
5. 分别接入拍摄页、两套 Fn 页、纵横比选择页的创建、刷新、旋转和销毁。核验方向 0/1/2、display mapping、原厂比例清除、当前高亮与已确认比例的区别。
6. 构建 AP AArch64 freestanding 模块时明确固定 VA、栈对齐、重定位与调用约定；纯整数/原子读侧使用 `-mgeneral-regs-only -mno-outline-atomics`。CP 按 ARM/Thumb 调用状态接跳板，AVCAM 按 AArch64 链接和回填。检查未定义符号、自动 thunk、段重叠、BSS 清零和内存边界。
7. 打包后重新提取最终文件，对照预期输出身份；核对分区 CRC、数据块和签名。只有构建目录中的候选文件正确还不够，需验证实际签名包中的成员。
8. 实机分别验证浏览/取消/确认/重启、四种比例、横竖连续切换、Fn 与选择页、成片和 RAW；软件回放与实机结果分别记录。

本次选择页有 336 项原生创建/旋转/清除回放、3,475 项绘制检查和 3,968 项调用约定检查。最终包完成签名、739,727 个数据块、分区 CRC 和 76 个目标文件核验；维护者随后确认横竖屏正常。该确认来自单台 A7M4，未扩大为所有输出设备及全部参数页面的穷举结论。JPEG/RAW 有样片几何检查，HEIF 有实现与原生路径回放，尚无独立 HEIF 实拍尺寸测量。

文档配套清单中的 23 个 AP 预览跳转已重新读取最终文件验证，列有 VA、文件偏移、指令字节和目标。其余说明来自最终保留的实现和冻结验证证据。本次发布只补充方法文档与参考元数据，不改变已验收固件。
