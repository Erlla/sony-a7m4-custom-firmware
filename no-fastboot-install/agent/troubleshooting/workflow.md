# 备份、补丁、菜单与安装

[返回索引](README.md) · [机器检索索引](index.json)

先核对当前任务和构建。以下是已归纳的历史经验，不是对新故障的自动诊断；处理始终服从当前正式入口的待办。

<a id="usb-012"></a>
## USB-012 · status.json 丢失或启动后一直停在旧失败页

**匹配线索：** `status.json`、`No such file or directory`、`需重新检查`、`操作需要检查`。

**阶段：** 本地状态装载。**原因状态：** 同症状有多个可能原因。

**历史原因：** 一例旧 current 索引仍指向已不存在的 run；另一些只是界面继承了历史状态。未决写入不能被界面重置消除。

**本轮应核对：** 区分本地状态读取失败与设备失败，查原任务/独立控制记录和阶段；先确定哪些记录实际存在。

**处理：** 使用程序原任务核对入口。只有正式状态机证明可结束或启动新任务时才推进；向用户说明缺哪份证据。

**不要这样做：** 不补造 status.json、不删除 current/claim、不把历史成功视作当前新固件已兼容。

**证据与验证范围：** 2026-10-22 归档证明支持一次特定旧任务结案；该一次性处理不是通用的删除/重建配方。

<a id="usb-013"></a>
## USB-013 · 保存快照或控制记录失败

**匹配线索：** `snapshot_ref.json`、`.tmp`、`WinError 5`、`WinError 32`、`WinError 33`。

**阶段：** 本地文件与状态保存。**原因状态：** 同症状有多个可能原因。

**历史原因：** 已确认过长临时路径创建失败；另有 Windows 文件共享方式导致原子替换失败的复现。具体占用进程在原现场未得到证明。

**本轮应核对：** 读取异常路径长度、errno/winerror、磁盘可用性与失败发生在写前还是写后。不要把任何 FileNotFoundError 都当成长路径。

**处理：** 未有设备任务时可选短、可写的新目录完整解压；活动目录保留原位，按状态核对。使用已包含短临时名、长路径 I/O 和共享替换修复的构建。

**不要这样做：** 不搬动活动目录、不自动关闭安全软件或同步软件、不在写后保存失败时宣称没有写入。

**证据与验证范围：** 2026-10-24 长路径案例；10-25 真实 Windows 文件共享复现与保留旧有效状态的有限重试通过。

<a id="usb-014"></a>
## USB-014 · 菜单准备找不到旧发布清单

**匹配线索：** `app/provider/release.json`、`provider\release.json`、`MENU_PREPARATION_RETRY`。

**阶段：** 本地菜单封装。**原因状态：** 历史案例已确认。

**历史原因：** 精简包已使用中央 app/release.json，但两条菜单控制器还引用旧 provider 清单。此前材料生成测试未覆盖 seal/validate。

**本轮应核对：** 确认 p1 完整回读结果、异常精确路径，以及是否已有 menu plan/start/execution；不能仅凭错误名跳到新菜单任务。

**处理：** 使用程序提供的“继续准备菜单”待办，按已保存证明继续；这个历史修复不需要重新写 p1。

**不要这样做：** 不复制或伪造 release.json，不编辑哈希，不用 start 重跑已完成的补丁。

**证据与验证范围：** 2026-10-25 实际记录定位；两条菜单真实材料封装、校验与写前边界开发测试通过。

<a id="usb-015"></a>
## USB-015 · 705/766 或 766/766 后很久没有变化

**匹配线索：** `705`、`766`、`offline_replay`、`PATCH_PREPARING`、`receiver_replay_writer.py`。

**阶段：** 备份后本机准备。**原因状态：** 同症状有多个可能原因。

**历史原因：** 旧日志每 64 块打印一次，所以 705 不等于第 705 块卡死。早期日常流程还运行完整仿真；后期又有重复镜像分析和旧进度残留。

**本轮应核对：** 查询原任务的当前 phase、heartbeat、progress 和本地日志末尾，确定仍在 USB 读取、本机准备还是实际写入；不要仅按最后块号判断。

**处理：** 新构建使用持续 status 反馈，向用户说明阶段。日常不再执行仿真/故障注入；纯计算热点已优化，但等候期间仍不重发任务。

**不要这样做：** 不因无输出拔线、强杀后台或重复 start；开发基准提速不能当作相机安装总时间承诺。

**证据与验证范围：** 2026-10-24 日志定位写前回放；实验 r6 离线同输入材料生成/复核约39.94→21.74秒，非整机实测。

<a id="usb-016"></a>
## USB-016 · libJiritsu 与离线绑定不同

**匹配线索：** `Current library differs from offline binding`、`/usr/lib/libJiritsu.so`、`当前相机固件非6.02版本`。

**阶段：** 服务库兼容检查。**原因状态：** 历史案例已确认。

**历史原因：** 一份真实返回库长度、ELF 布局与绑定基线不同；USB 帧和保存文件一致，排除了该次传输截断。界面版本标签不能证明库兼容。

**本轮应核对：** 读取完整原始异常、实际/预期库摘要和长度，以及任务是否已到 READ_STARTING。具体相机版本未知时如实记录未知。

**处理：** 按正式流程停止并恢复连接，保留摘要供维护者适配；用户可通过本包说明核对受支持固件来源。

**不要这样做：** 不改绑定 SHA 放行、不绕过兼容检查、不把“非6.02”文案当成工具已读出实际版本号。

**证据与验证范围：** 2026-11-07 完整传输与 ELF 核对证明不同构建；该陌生库未因此获得写入兼容验收。

<a id="usb-017"></a>
## USB-017 · Unknown updater library

**匹配线索：** `Unknown updater library`、`updater_lineage`、`content_stock`、`content_user`。

**阶段：** p1 内容分析。**原因状态：** 同症状有多个可能原因。

**历史原因：** 历史一例是自有公钥更新器误走官方分类器；其他未知库仍可能是真正未适配。取消版本页白名单不代表所有二进制布局都可用。

**本轮应核对：** 查实际 updater_lineage、库摘要及本轮完整备份结果，核对构建是否包含对应已审查路线。

**处理：** 由正式内容分类决定官方或自定义路线；不匹配时停止写入，按待办恢复，并整理实际摘要。

**不要这样做：** 不把所有未知库强行当作自定义，不因版本显示相同就复用另一机身 p1。

**证据与验证范围：** 2026-10-24 自定义更新器分类遗漏已定位并修复；未知新构建仍需独立分析。

<a id="usb-018"></a>
## USB-018 · 原生预读拒绝 phase 90 / error -2

**匹配线索：** `Native p1 read rejected`、`phase 90`、`phase=90`、`error -2`、`flags=3`。

**阶段：** 只读备份或菜单预读。**原因状态：** 原现场唯一根因未确认。

**历史原因：** 旧原生帧把多个失败对象归到同一 errno，不能由 -2 推断 p1 不存在。fd 关闭竞态是代码中找到的候选，但原现场缺失足够诊断，唯一根因未确认。

**本轮应核对：** 查新诊断的 step/errno、读取字节数、reader result/cleaned 匹配证明、是否为写后回读，以及 window_started。旧帧没有字段时写明原因未知。

**处理：** 等待程序对同任务的有限清理确认；只在其明确允许恢复时走普通 USB 恢复。若缺清理证明，按当前待办与用户相机状态处理，不伪造完成。

**不要这样做：** 不重发 START，不补写 cleaned，不将写后回读失败当作写前只读失败；不得据此建议直接刷另一镜像。

**证据与验证范围：** 2026-11-08 真实帧回放保留原错误，清理与恢复分类已修；后续新增诊断及只读审计有限复查经过原生/主机替代测试。

<a id="usb-019"></a>
## USB-019 · p1 完成，但菜单没有就绪

**匹配线索：** `HANDOFF_NOT_READY`、`final_unplug_ready`、`menu_ready=false`、`seconds_remaining`。

**阶段：** 菜单交接。**原因状态：** 同症状有多个可能原因。

**历史原因：** p1 完成、RAM 窗口启动、普通身份出现和可拔线交接是不同事实；普通身份等待、窗口时间不足或交接检查异常都可能导致未就绪。

**本轮应核对：** 读取 p1_operation_complete、menu_ready、window_started、原始 reason 和剩余时间。旧版 passed=true 不足以证明可安装。

**处理：** 只按当前 pending 处理。需要相机正常重启时先确认没有正在安装并等待用户回复；只恢复旧会话，不重新写 p1 或自动开新窗口。

**不要这样做：** 不能因还有561秒或 p1 已完整回读就告诉用户执行安装。已实际开始安装时也不能因窗口过期要求断电。

**证据与验证范围：** 2026-11-08 增加交接失败具体原因及恢复分流，状态检查以明确 menu_ready 和当前窗口为准。

<a id="usb-020"></a>
## USB-020 · 软件更新菜单灰色

**匹配线索：** `软件更新是灰色`、`菜单灰显`、`无法点击`、`更新按钮`。

**阶段：** 相机菜单观察。**原因状态：** 同症状有多个可能原因。

**历史原因：** 历史离线追踪发现两处不同菜单版本条件，早期只准备一处不足；连接状态、包放置和相机条件也会影响入口。电池百分比本身不是本案例根因证据。

**本轮应核对：** 先查程序 menu_ready 和窗口，再询问用户 USB 是否按提示断开、卡槽1文件是否放好、屏幕实际提示；不要把“灰色”误记成包校验拒绝。

**处理：** 按当前正式菜单待办逐步指导，未就绪先解决本轮准备，不让用户试执行。只有确认页接受目标版本后才继续安装。

**不要这样做：** 不自行改 RAM 地址、补第三处猜测补丁，不能用旧窗口成功证明本次可用。

**证据与验证范围：** 2026-10-23 两处准备后用户进入确认页；后续 r5 本机确认6.02→6.01，其他条件仍逐次核对。

<a id="usb-021"></a>
## USB-021 · 更新失败：快闪6下、慢闪8下

**匹配线索：** `快闪6下`、`慢闪8下`、`6快8慢`、`0x86`。

**阶段：** 用户相机安装。**原因状态：** 同症状有多个可能原因。

**历史原因：** 一个旧6.01候选把版本布尔判断写成返回false，机内回读确认后修正，用户最终成功回官方6.02。但相同LED节奏并非此原因的唯一映射。

**本轮应核对：** 询问实际屏幕/灯状态和能否正常拍摄，核对使用包的来源及可得摘要、现存更新/补丁记录。版本页“6.01”不能区分旧候选与修正版。

**处理：** 记录为用户报告安装失败，按当前失败待办收集状态。具体修复需针对实际证据与授权；普通 Agent 流程不自行切入 Fastboot。

**不要这样做：** 不直接断言公钥错误、不重新签包或修改补丁、不套用另一机身备份；不能凭这个码指示立即断电。

**证据与验证范围：** 2026-10-24 特定机身p1回读、限定修复及用户安装验收支持该历史原因；进入机内旧包的选择过程仍有证据边界。
